# Auth & Ledger Architecture — Implementation Spec

Target codebase: `app` (generic Go backend + Svelte SPA frontend).
Stack: Go, Postgres (no Redis), Svelte (not SvelteKit), Zitadel (self-hosted), TigerBeetle, Caddy.

This document describes decided architecture. Implement accordingly; do not introduce
alternative patterns (e.g. Redis sessions, SPA-direct OIDC, local JWKS validation) without
flagging the deviation first.

---

## 1. Identity provider: Zitadel

- Self-hosted Zitadel instance.
- **One org, one project, one app** in Zitadel — app type: **Web application, confidential**
  (has a client secret). This single app represents the Go backend. The Svelte SPA is not
  registered as a separate Zitadel app and never communicates with Zitadel directly.
- Roles are defined once at the **project** level (e.g. `admin`, `user`, whatever the domain
  needs) and read via role-grant claims on the token.
- 2FA: leave org-level "Force MFA" **off**. Users opt in/out themselves via Zitadel's
  self-service profile UI. No per-user enforcement toggle needed at launch.
- Social login (if/when enabled): no backend code changes required — same callback handles it.
- Self-registration, forgot-password, MFA enrollment: all handled by Zitadel's hosted login UI.
  Backend has no register/forgot-password/MFA endpoints of its own.

## 2. Auth pattern: Backend-for-Frontend (BFF)

The Svelte SPA never talks to Zitadel and never sees a Zitadel token. It only ever calls the
Go backend's own endpoints.

### Flow (implement exactly this sequence)

1. `GET /auth/login` (Go) — full browser navigation from Svelte, not a fetch.
   Go generates PKCE verifier/challenge + `state`, stashes them (short-lived, signed cookie
   or equivalent — no Redis), redirects (302) browser to Zitadel `/authorize` with Go's
   `client_id`, PKCE challenge, `redirect_uri` pointing back to Go's `/auth/callback`.
2. Browser interacts with Zitadel's hosted UI directly (login, register, MFA, password reset,
   social login — all Zitadel's problem, not ours).
3. Zitadel redirects browser to `GET /auth/callback` on Go with `code` + `state`.
4. Go validates `state`, exchanges `code` for tokens at Zitadel's token endpoint
   (server-to-server call, using client secret + PKCE verifier). Tokens never reach the browser.
5. Go creates an app session (see §3) and sets **one** session cookie:
   `HttpOnly`, `Secure`, `SameSite=Strict`. Cookie value is opaque — no JWT, no token data.
6. Go redirects browser to the post-login destination (e.g. `/dashboard`).
7. `POST /auth/logout` — Go destroys the session, clears the cookie, optionally hits
   Zitadel's end-session endpoint.

Use the `zitadel-go` SDK for steps 1–4 (PKCE, discovery, callback handling, token verification
helpers). Do not hand-roll PKCE or signature verification.

## 3. Sessions

- **Library: `scs`** (github.com/alexedwards/scs).
- **Store: Postgres** (`scs/postgresstore`) — no Redis anywhere in this stack.
- Session holds: internal session ID (scs-managed) → mapped data including the Zitadel
  access token, refresh token, and expiry. Store these as session values, not as separate
  application logic.
- Token validation on incoming requests: **introspection endpoint**, not local JWKS
  validation. Acceptable given Go and Zitadel are on the same machine/close network — no
  meaningful latency cost, and it gives real-time revocation awareness for free.
- Token refresh: when access token is near/past expiry, use the stored refresh token to get
  a new one from Zitadel server-side. Transparent to the frontend.

## 4. User identity mapping

- Zitadel's `sub` claim is the canonical external identity, but **do not use `sub` as the
  primary key anywhere outside the identity-mapping table.**
- On first successful login for a given `sub` (i.e. no matching row found), just-in-time
  provision: generate a new **UUIDv7** and insert a row into the app's own `users` table,
  e.g.:

  ```sql
  CREATE TABLE users (
      id UUID PRIMARY KEY,           -- UUIDv7, generated by app
      zitadel_sub TEXT UNIQUE NOT NULL,
      -- other app-owned profile fields
  );
  ```

- All other application tables (including TigerBeetle-linked data, see §5) reference
  `users.id` (the UUIDv7), never `zitadel_sub`, directly.
- Reasoning: insulates the rest of the system from any future identity-provider change, and
  keeps a single deliberate point (`zitadel_sub` column) where identity can be erased for
  privacy/GDPR purposes without touching downstream data.

## 5. TigerBeetle integration

- **User-linked IDs: UUIDv7.** Same UUID generated in §4 is reused for TigerBeetle
  interaction — chosen for time-sortability and to avoid monotonic-ID collision issues
  across nodes.
- Do **not** put `zitadel_sub` into TigerBeetle at all, ever — only the app-generated UUIDv7.
- Mapping approach:
  - If a user has exactly one TigerBeetle account: the UUIDv7 (as raw 16 bytes → `UInt128`)
    may be used directly as the TigerBeetle `Account.id`.
  - If a user has multiple TigerBeetle accounts (e.g. per-ledger/per-asset — likely for this
    domain): each account gets its own TigerBeetle-generated ID, and the user's UUIDv7 goes
    into `user_data_128` on every account belonging to that user, to link them back.
- Convert UUIDv7 → TigerBeetle `UInt128` by reinterpreting the UUID's 16 raw bytes — no
  string parsing, no reformatting.
- Privacy note: erasure requests are handled by deleting the `users` row / `zitadel_sub`
  mapping in Postgres, not by touching TigerBeetle (accounts/transfers are immutable and
  cannot be deleted). Once the mapping row is gone, TigerBeetle records can no longer be
  linked to a real person.

## 6. Email / SMS: custom, via webhooks

- Do **not** use Zitadel's built-in SMTP/Twilio integrations.
- Configure Zitadel's **generic HTTP notification provider** instead — Zitadel calls out to
  an endpoint the app controls for every email/SMS it needs to send (registration
  confirmation, password reset codes, OTP codes, etc.), and the app's own webhook handler
  dispatches via whatever email/SMS provider it's actually using.
- This webhook endpoint is **inbound to the app**, called by Zitadel — treat it as a
  privileged internal endpoint (see §7), not part of the public API surface.

## 7. Network/routing: webhook isolation via Caddy

- Public API (`/api/*`) and internal webhooks (`/webhooks/*`, including the Zitadel
  notification webhook and any SMS-provider delivery-status callbacks) are **not** treated
  the same way at the network layer.
- **Preferred approach (self-hosted Zitadel on the same private network):** do not route
  webhook traffic through Caddy's public listener at all. Bind the Go webhook handler to a
  private-network-only address/port; Zitadel calls it directly over the internal network.
  Public Caddy config has no route for `/webhooks/*` — a public request to that path 404s
  because the route doesn't exist, not because it was filtered.
- **Fallback (only for callers that are unavoidably public** — e.g. a third-party SMS
  provider's delivery-status callback that must come from the public internet): use Caddy's
  built-in `remote_ip` matcher to allowlist known source IPs/CIDR ranges for that path,
  stacked **on top of** signature/HMAC verification in the Go handler — never as a
  replacement for it.
- All webhook handlers, regardless of network exposure, must verify an authenticated
  signature or shared secret on every request. Network isolation is defense-in-depth, not a
  substitute for auth.

---

## Summary of explicit decisions (do not deviate without flagging)

| Area | Decision |
|---|---|
| Zitadel topology | 1 org, 1 project, 1 app (confidential Web app) |
| Auth pattern | BFF — Go is sole OIDC client, SPA never touches Zitadel |
| Session library | `scs` |
| Session store | Postgres (no Redis) |
| Token validation | Introspection endpoint (not local JWKS) |
| 2FA enforcement | Off — self-service opt-in only |
| User ID format | UUIDv7, app-generated, keyed off Zitadel `sub` |
| TigerBeetle ID | Same UUIDv7 (direct or via `user_data_128`) |
| Email/SMS | Custom, via Zitadel's generic HTTP webhook provider — not Zitadel's built-in SMTP/Twilio |
| Webhook network exposure | Internal-only where possible (self-hosted, same network); `remote_ip` + signature only when a caller is unavoidably public |
